# MCPVault 회의·아이디어·브레인스토밍 강화 계획

> 구현 후속 상태: [2026-09-08 체크포인트](implementation-status-2026-09-08.md).
> 아래 본문은 조사 당시 승인 계획을 보존한 것이며, 전체 구현 완료를 뜻하지 않는다.

작성일: 2026-09-08

상태: 조사 및 인계 계획 — 기능 미구현

구현 인계 대상: `llm_wiki` (1번 에이전트, 작업 ID `01a058d8-4e01-7e63-a80f-1ad3ec9dbb0e`)

> 이 문서는 1번 에이전트가 현재 작업을 마친 뒤 찾아볼 수 있도록 보존한 인계 자료다. 이 문서를 저장하거나 전달하는 것은 즉시 구현을 시작하거나 현재 작업을 중단하라는 지시가 아니다. 문서 작성 세션은 이 기능을 구현하지 않는다.

## 1. 목표와 확정 방향

**에이전트가 상황에 맞는 회의 기법을 선택하고, 토론을 진행하며, 위임된 범위 안에서 결정과 후속 과제까지 연결한다.**

사용자가 직접 선택한 방향은 다음과 같다.

- 에이전트가 주요 참여자이며, 사람도 방향 설정·기여·결정에 참여한다.
- 양식과 안내뿐 아니라 자동 진행자를 제공한다.
- 명시적으로 위임된 범위에서는 결정 확정과 후속 과제 생성을 허용한다.
- 일부 핵심 기법만 구현하지 않고, 아래 조사 기법 전체를 실행 가능한 절차로 제공한다.
- 에이전트 수를 기법의 역할 수에 맞춰 늘리지 않는다. 기존 에이전트가 순차적으로 참여하며 중단 후 이어간다.
- 구현은 1번 에이전트에게 인계한다. 이 문서는 나중에 참고하기 위한 기록이다.

기존 Workshop·Idea Lab·Work·Decision Record·연구 기록·Canvas를 확장한다. 회의록이나 아이디어를 위한 별도 데이터베이스, 모델 실행 서버, 스케줄러는 만들지 않는다.

기본 흐름은 다음과 같다.

**회의 목적·권한 설정 → 사전 자료 → 기법 선택 → 개별 제안 → 공유·분류 → 반론·평가 → 결정 → 후속 과제 → 회고**

모든 회의에 전체 절차를 강제하지 않는다. 자동 진행자가 목적에 필요한 절차만 구성하고 선택 이유를 남긴다.

## 2. 현재 구현에서 이어받을 부분

2026-09-08에 읽기 전용으로 확인한 내용이다. 후속 작업으로 파일이 바뀔 수 있으므로 착수 시 최신 코드와 담당자를 다시 확인한다.

- `src/ideation.ts`와 `src/ideation-tools.ts`에 기존 Idea Lab 및 Workshop 서비스가 있다. Workshop은 `diverge`, `cluster`, `critique`, `evaluate`, `synthesize`, `decide`, `closed` 단계를 사용한다.
- 기존 Workshop은 agenda, 진행자 표시, 참여 기여, 단계 변경, 종합을 지원한다. 기여의 `expectedPhase`는 선택적이며 기법별 세부 단계는 없다. 진행자 표시 자체를 새 기능의 권한 검사로 간주하지 않는다.
- 일반 기여 본문은 280자, 긴 설명과 종합은 4,000자 제한이다. 구조화된 기법 제출을 추가할 때 기존 짧은 기여 형식은 유지한다.
- 기존 생성 재시도와 연구 Workshop의 Work claim 검증을 재사용한다. 새 회의 기능 때문에 기존 연구 작업·Workshop이 중복 생성되어서는 안 된다.
- `src/community-participation-activities.ts`에 `joint-research`, `evidence-puzzle`, `collaborative-creation` 활동이 있다. 커뮤니티 참여 서비스는 호스트 실행과 예산을 전제로 하며 모델을 깨우지 않는다.
- 기존 `wiki.decision_record`, Work 프로젝트·과제·claim, 연구 양식 및 `wiki.bridge_candidates`를 결과 연결에 사용한다.
- 기존 `wiki.canvas_view`와 `wiki.canvas_export`는 scope와 원본 fingerprint, 출력 revision을 검증한다. 지도 화면을 위해 이 검증을 우회하거나 별도 그래프 저장소를 만들지 않는다.

## 4. 제품·인터페이스 변경

### 4.1 공통 회의 계약과 진행 엔진

기존 Workshop에 선택적인 진행 설정을 추가한다. 설정이 없는 기존 Workshop은 현재 방식으로 계속 동작하며 자동 진행을 켜지 않는다.

관리되는 회의에는 다음 내용을 기록한다.

- 목적, 범위, 성공 기준, 원본 자료와 revision.
- 선택한 기법과 버전, 실행 단계, 현재 단계 ID, 반복 회차.
- 진행 책임 계정, 참여 계정, 결정권자와 위임 범위.
- 완료된 점검, 대기 사유, 다음 행동, 재개 조건.
- 종합·결정·후속 과제로 이어지는 원본 기여의 참조.

기법의 세부 단계는 기존 Workshop 단계 아래에 둔다. 여러 모자 검토가 같은 상위 단계에 속하더라도 단계 ID로 구분한다. 늦게 도착한 제출물이 다음 모자의 의견으로 섞이지 않도록 한다.

기법 정의는 실행 코드가 아닌 고정된 데이터로 제공한다. 초기 버전에서는 임의 스크립트나 사용자가 작성한 절차 코드를 실행하지 않는다.

### 4.2 동적 endpoint와 기존 API 확장

고정 MCP 도구 다섯 개는 유지한다. 아래 신규 이름은 계획상의 동적 endpoint ID이며, 아직 사용 가능한 기능이 아니다.

| 인터페이스 | 변경 |
| --- | --- |
| **`workshop.methods` — 신규, 읽기 전용** | 기법 목록이나 선택한 기법 하나의 목적·준비 조건·단계·산출물·원형과 변형의 차이를 반환한다. |
| **`workshop.facilitation` — 신규, 읽기 전용** | 현재 단계, 충족·미충족 조건, 대기 사유, 필요한 자료와 실행 가능한 다음 행동 하나를 반환한다. |
| **`workshop.facilitation_update` — 신규, 변경 작업** | 진행 설정, 단계 전환, 일시정지·재개, 담당 인계, 위임 변경을 처리한다. revision과 재시도 키를 요구한다. |
| **기존 `workshop.create`** | 선택적 기법 구성, 참여 계획, 진행·결정 위임 설정을 받는다. |
| **기존 `workshop.contribute`** | 관리되는 회의에서는 현재 단계 ID와 revision을 요구한다. 아이디어 묶음·그룹·지도 연결·투표·체크 결과를 위한 제한된 구조화 제출을 지원한다. |
| **기존 단계 변경·종합 API** | 관리되는 회의의 진행 조건과 담당 권한을 공통 서비스에서 검사한다. 이전 API를 통한 우회도 막는다. |
| **기존 Canvas 조회·내보내기** | Workshop 지도 모드를 추가한다. 기존 출력 revision·원본 fingerprint·scope 검증을 재사용한다. |

기법 카탈로그와 진행 로직은 기존 대형 ideation 서비스에서 분리된 모듈로 구현한다. MCP·REST·커뮤니티 참여 경로는 같은 서비스를 호출한다. 모든 변경 작업을 읽기 전용 거부 목록과 capability 모델에 반영한다.

새 응답은 기본 6,000자·최대 12,000자로 제한하고, 큰 회의는 커서로 이어 읽는다. 단계 판정에 필요한 기여를 모두 확인하지 못했다면 완료를 추정하지 않고 남은 범위를 표시한다.

### 4.3 회의 산출물

회의 기여는 기존 Workshop 하위 Markdown 기록에 저장한다. 긴 설명은 노트 참조로 연결하고 전체 본문을 반복 복사하지 않는다.

- 아이디어에는 안정적인 ID와 원안·확장·반론 관계를 남긴다.
- 그룹화는 원안을 삭제하거나 합치지 않고 소속 관계로 기록한다.
- 투표는 실제 인증 계정별로 집계한다. 같은 계정의 여러 세션과 역할 변경은 별도 표가 되지 않는다. 계정 수를 인간 수나 통계적 독립성으로 해석하지 않는다.
- 체크리스트는 `미확인·충족·미충족·해당 없음`을 구분한다. 확인자와 근거 또는 사유를 보존한다.
- 종합에는 채택안뿐 아니라 제외안·소수 의견·불확실성·재검토 조건도 포함한다.
- 마인드맵의 가지와 연결은 Markdown의 명시적 관계를 따른다. 위치·색상·그룹은 근거의 강도나 인과관계를 뜻하지 않는다.

초기 버전은 공개 Workshop의 기존 범위를 유지한다. 독립적으로 작성하도록 안내하고 첫 제출용 화면에서 다른 제안을 생략할 수 있지만, 이를 비밀 투표나 접근이 차단된 블라인드 제출로 표현하지 않는다. 비공개 내용과 그 존재를 공개 회의의 후보·요약·지도에 노출하지 않는다.

비공개 회의실·녹음·전사·화상회의·외부 화이트보드 연동은 이번 범위에 포함하지 않는다.

## 5. 자동 진행자와 위임된 결정

### 5.1 기법 선택과 실행

자동 진행자는 현재 요청과 자료를 읽고 기법을 선택한다.

- 문제 자체가 불명확하면 HMW.
- 대안이 필요하면 Brainwriting, 기존 안을 바꾸려면 SCAMPER.
- 다양한 관점을 검토하려면 6 Hats.
- 관계를 이해하려면 마인드맵, 제안이 많으면 Affinity Mapping.
- 참여자의 의견을 고르게 모으려면 NGT 또는 참여 인원이 갖춰진 1-2-4-All.
- 선택이 필요하면 개별 평가·투표와 DACI.
- 실행 전 위험 검토는 Premortem, 작업 후 학습은 회고, 사건 분석은 Postmortem.

사용자가 기법을 지정하면 그 기법을 우선한다. 원형의 준비 조건을 충족하지 못할 때는 부족 조건과 변형 여부를 드러낸다.

Page-led 문서와 체크리스트는 다른 기법의 준비·종료 절차로 함께 사용할 수 있다. 한 회의의 자동 구성은 기법 최대 4개·세부 단계 최대 32개로 제한한다. 더 큰 과제는 연결된 후속 회의로 나눈다. 전체 카탈로그를 한 회의에 모두 실행하지 않는다.

6 Hats의 기본 절차는 **진행 설정 → 정보 → 대안 → 장점 → 위험 → 직관·선호 → 종합**으로 둔다. 이는 제품의 기본 진행 순서이며 유일한 정식 순서라고 주장하지 않는다. 에이전트의 직관은 근거가 없는 잠정 판단으로 표시하고, 사람의 감정을 실제 관찰한 것처럼 만들지 않는다.

참여자가 부족한 경우 가상의 참석자를 생성하지 않는다. 인원 조건이 있는 기법은 기다리거나 축약 방식을 명시한다. 한 에이전트의 여러 관점 검토는 단독 검토로 기록하며 독립된 동료 검토나 합의로 계산하지 않는다.

### 5.2 진행 권한과 결정 권한

위임에는 대상 회의·프로젝트, 허용된 결정 종류, 후속 과제 생성 범위, 결정권자, 철회 상태를 기록한다.

- 회의 진행 위임은 해당 회의의 관리 권한이 있는 계정만 설정한다.
- 프로젝트 관련 위임은 기존 프로젝트 권한을 확인한다.
- 위임 기록은 접근 권한을 새로 부여하지 않는다. 모든 변경에서 현재 인증·scope·프로젝트 권한을 다시 확인한다.
- 자연어로 작성한 업무 범위의 충족 여부는 에이전트가 판단한다. 서버는 계정·대상·허용 작업·현재 revision을 검사하며, 업무 내용까지 자동으로 검증했다고 주장하지 않는다.
- 위임이 없거나 범위가 불명확하면 진행·종합은 이어가되 결과는 제안 상태로 남긴다.

위임 범위 안에서 결정이 가능하면 기존 `wiki.decision_record`에 결정 이유·대안·근거·반대 의견·재검토 조건을 기록한다. 후속 과제는 지정된 기존 프로젝트에 생성한다. 프로젝트가 없으면 임의로 만들지 않고 필요한 조건을 남긴다.

결정·과제·회의 연결에는 안정적인 출력 ID와 실행 영수증을 사용한다. 결정 저장 후 중단되었더라도 재개 시 같은 결정을 찾고 남은 과제만 생성한다. 외부 발송·배포·구매·실험 실행은 회의 결정만으로 새 권한을 얻지 않는다.

### 5.3 중단·자원·반복 제어

- MCP 서버는 모델을 호출하거나 서브에이전트를 생성하지 않는다.
- 호스트의 기존 실행 경로에서 회의 모델 작업을 한 번에 하나씩 실행한다. 다른 호스트나 무관한 작업의 자원까지 서버가 통제한다고 주장하지 않는다.
- 자율 참여는 기존 기본 OFF·4시간 간격·하루 최대 6회·회당 실질 행동 1개·5분·사용자 작업 중 유예 정책을 공유한다.
- 사용자가 직접 시작한 회의는 해당 요청의 실행 예산을 따른다. 자율 참여 제한을 우회하는 별도 타이머는 만들지 않는다.
- 일반 재논의는 자동으로 한 번만 반복한다. 6-3-5처럼 기법 자체가 요구하는 회차는 별도로 정의한다.
- 자료 부족·동료 부재·권한 변경·원본 변경·예산 소진은 대기 사유와 재개 조건으로 남긴다.
- 시간 경과만으로 합의·검증·체크 완료를 만들지 않는다.
- 진행 전환은 revision 검사와 재시도 키로 보호한다. 여러 세션이 동시에 진행하더라도 한 전환만 반영한다.

연구형 회의는 기존 `wiki.bridge_candidates`와 연구 가설 양식을 사용한다. 결정으로 이어진 관찰과 실패한 대안은 연구 기록·기억·다음 회의의 사전 자료로 연결한다. 개인 기억은 원래 scope를 유지하고 공개 회의에서는 허용된 공개 자료만 사용한다.

## 6. 구현 순서와 검증

### 6.1 구현 순서

1. **기법 카탈로그와 공통 진행 계약** — 16개 기법과 명시된 변형의 단계·입력·산출물·완료 조건을 작성하고, 기존 Workshop과의 호환성을 구현한다.
2. **구조화된 기여와 회의 산출물** — 아이디어 관계, 분류, 체크리스트, 평가·투표, 마인드맵, 회의 종합을 구현한다.
3. **자동 진행과 위임된 결정** — 단계별 다음 행동, 담당 인계, 중단 후 재개, 권한 검사, 결정·과제 생성의 중복 방지를 연결한다.
4. **기억·연구·커뮤니티 통합과 평가** — 기존 참여 경로와 연구 기록을 연결하고, 모든 기법의 실행 검증과 실제 사례 비교를 마친다.

이 순서는 구현을 나누기 위한 것이며, 일부 기법을 안내 문서만 제공하는 상태로 완료 처리하지 않는다.

### 6.2 필수 검증

- 16개 기법 각각의 정상 종료와 미충족 조건을 테스트한다.
- 6 Hats의 단계 혼입, Brainwriting 원형·변형 구분, 1-2-4-All의 인원 부족을 확인한다.
- 재시도·동시 제출·동시 단계 전환·담당 인계·중단 후 재개에서 중복이 생기지 않는지 확인한다.
- 같은 계정의 여러 세션이 투표나 독립 참여 수를 늘리지 않는지 확인한다.
- 위임 철회, 인증 만료, 프로젝트 권한 변경, 이전 API를 통한 우회를 차단하는지 확인한다.
- 숨겨진 자료·원본·집계가 응답과 지도에 노출되지 않는지 확인한다.
- Markdown의 matching backtick/tilde fenced 예시가 실제 제출·체크 완료·결정으로 해석되지 않는지 확인한다.
- Canvas 원본 변경과 결정 근거 revision 변경을 감지하는지 확인한다.
- 응답 크기·커서·실행 예산과 기존 다섯 MCP 도구를 유지하는지 확인한다.
- 기존 연구 Workshop claim, 공개 변경 재시도, 커뮤니티 참여 영수증을 그대로 지원하는지 확인한다.

실제 평가는 제품 아이디어·설계 선택·연구 연결·위험 검토·회고·사건 분석에서 각 2개씩, 총 12개 과제를 사용한다. 기존 자유형 Workshop과 새 진행 방식을 같은 자료·모델 설정·실행 예산으로 비교한다.

측정 항목은 유용한 대안, 근거 추적, 반론 보존, 결정·과제의 실행 가능성, 중복·잘못된 확정, 토큰·시간·기록 부담이다. 기법별 회귀 테스트 통과를 실제 회의 품질 향상으로 해석하지 않는다. 실제 평가를 수행하지 못했으면 미실시로 남기며 수치를 추정해 채우지 않는다.

코드 구현 후 표적 테스트 → `npm run build` → `npm test -- --maxWorkers=1` → `git diff --check` 순서로 검증한다. 다른 세션의 빌드·모델 평가와 겹치지 않게 조율한다. 생성된 `dist`를 소스와 함께 검토한다. 이 문서 저장만으로는 빌드나 테스트를 실행할 필요가 없다.
