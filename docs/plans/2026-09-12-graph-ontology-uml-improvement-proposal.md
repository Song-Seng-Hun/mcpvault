# MCPVault 그래프·온톨로지·UML 개선 제안

작성일: 2026-09-12. 상태: **선행 P1/P2/P3 전달 완료, 1단계 계약 추출 검증·NAS 배포 완료**.

현재 상태: P3까지 사용자 포크 `main`의 `16dcb945`로 전달했다. `llm_wiki`와
조율하여 본 작업이 계약 1단계의 공유 소스·NAS 배포·단일 검증 시간을 맡는다.
1단계 소스·인접 테스트·strict build와 두 독립 정적 검토, 전체 회귀 검증 및
NAS 배포·실제 조회가 완료됐다. 포크 전달은 Git 기록으로 확인한다. 아래 작성
당시의 P1 미완료·메모리 상황은 과거 기록이며 현재 상태가 아니다.

승인 기록: 사용자의 “좋아 진행해”에 따라 A안의 계약 통합·근거 표현·로컬 검증·UML 및 기존 인덱스 측정을 진행한다. B/C 저장소 설치, RDF 내보내기와 렌더러 설치의 별도 승인 경계는 유지한다. 승인 자체는 구현·검증·배포 완료를 뜻하지 않는다.

## 결론과 범위

개선 여지는 있다. 다만 새 그래프 DB보다 **기존 관계 계약의 일관성, 근거 관계의 표현, 설계와 구현의 불일치 검출**을 먼저 개선한다. Markdown·Properties·원본·리비전·Git의 권위와 기존 다섯 MCP 도구를 유지한다. 별도 모델 서버, 유료 API, 그래프 DB, 자동 추론 게시를 이번 제안으로 설치하거나 활성화하지 않는다.

기존 승인된 P1 두 단계 검색 → P2 주제 패킷 → P3 로컬 Graphify와 별개인 후속 계획이다. 해당 작업을 완료한 뒤 착수하며, `llm_wiki` 작업의 Arkon 기반 후속 묶음과 공유 파일·단일 테스트 실행 시간을 다시 조율한다. P2의 요약 범위 검증이나 P3의 AST 추출기를 중복 구현하지 않는다.

배포·커밋·푸시는 사용자 포크 `Song-Seng-Hun/mcpvault`의 기존 `main`에서만 수행한다. PR, upstream contribution, 패키지/릴리스 게시, 새 브랜치, force-push는 하지 않는다.

## 1단계 — 기존 관계 계약 통합

목표는 의미를 바꾸지 않고 중복 정의가 어긋나는 것을 방지하는 것이다.

- 제안 파일 `src/graph-contract.ts`: 계약 버전, 기존 관계 이름·방향·상호 연결 여부, 현재 대상 종류 제한, 주장 속성과 관계의 매핑, 검색 프로파일별 허용 관계를 정의한다.
- `src/organization.ts`의 기존 공개 export는 호환성을 유지하고 공유 정의를 재사용한다. `src/llm-wiki.ts`의 `typedRelationTargetKindReason`과 주장 매핑을 작은 단위로 연결한다. 대형 서비스 전체를 리팩터링하지 않는다.
- `src/vault-graph.ts`와 P1 `src/question-graph.ts`는 필요한 프로파일만 소비한다. 모든 관계를 두 단계 검색에 자동 허용하지 않는다.
- `tests` 대상이 question/hypothesis/assumption인 기존 동작, `answers_questions`의 question 제한, 상호 연결의 전용 변경 절차를 보존한다.
- 계약 문서는 생성하거나 검사하되 문서를 읽었다는 사실을 의미 이해나 검토 통과로 표시하지 않는다.

검증: 먼저 기존 14종 관계·세 주장 매핑·상호 연결·대상 종류 오류를 고정하는 테스트를 작성한다. `src/graph-contract.test.ts`에 계약 누락/중복과 소비자 투영의 동등성 검사를 추가한다. 기존 입력·오류·직렬화 결과는 무회귀여야 한다. 새 엄격한 제약은 이 추출 작업에 섞지 않는다.

## 2단계 — 관계 발생 단위와 근거 계약

관계의 존재뿐 아니라 **어느 문서의 어느 리비전이 어디에서 그 관계를 주장했는지**를 보존한다.

- 제안 파일 `src/graph-assertion.ts`: 저장소 식별자, 문서 식별자/경로, 원본 리비전, 주장 ID, 관계 종류와 작성 방향, 목표 참조, 정확한 위치 또는 property path, 추출 방식·버전을 담는 파생 레코드를 정의한다.
- 문서 정체성, 문서 버전, 주장 ID를 분리한다. 선택적 `stable_id`는 충돌 검증 없이 전역 키로 쓰지 않는다. ID를 원본에 자동 추가하지 않으며 경로+리비전 대체 키는 버전 식별이라는 한계를 표시한다.
- 동일 문서쌍의 supports와 contradicts, 서로 다른 위치에서 나온 동일 관계를 원본 추출 목록에 각각 보존한다. 군집용 단순 그래프 투영은 별도 형식으로 둔다.
- 작성된 관계, 추출된 연결, 추론된 제안을 구분한다. Graphify의 코드 호출·테스트 참조는 지식의 진위나 테스트 통과를 뜻하지 않는다.
- ACL은 기존 정책 엔진이 판정한다. 그래프 연결·온톨로지 타입·관계의 상속은 접근권한을 부여하지 않는다. 가려진 노드의 수·경로·모호성 후보도 응답에 남기지 않는다.

후속 RDF 교환이 필요하면 관계 발생을 식별 가능한 assertion/provenance 레코드로 표현한다. RDF 그래프는 트리플의 집합이므로 단순 `(주어, 관계, 목적어)` 변환만으로는 중복 발생 위치를 보존할 수 없다. [RDF 1.1 Concepts](https://www.w3.org/TR/rdf11-concepts/)

출처 매핑에는 PROV-O의 Entity/Activity/Agent와 qualified relation 개념을 참고한다. 표준 용어를 쓰는 것만으로 원본의 신뢰성이나 독립적인 corroboration이 보장되지는 않는다. 실제 표준 내보내기는 별도 승인 범위다. [PROV-O](https://www.w3.org/TR/prov-o/)

검증: `src/graph-assertion.test.ts`에서 복수 관계·주장 앵커·잘못된 locator·동일 출처 중복·ID 충돌·리비전 변경·파일 삭제·권한 회수를 고정 fixture로 검사한다. P3 추출 결과를 소비하는 어댑터만 추가하며 두 번째 AST 추출기를 만들지 않는다.

## 3단계 — 가벼운 온톨로지 검증 프로파일

- 명칭·별칭, 관계 대상 종류, claim ID 유일성, 근거 리비전, 관계별 순환 정책을 기존 lint/preview 서비스에서 검증한다. 기존 경고와 거절의 구분은 유지한다.
- MOC 소속은 주제 구성이고 부모 링크는 탐색 구조다. 모든 MOC 링크를 클래스 상속으로 해석하지 않는다. depends_on 순환, MOC 부모 순환, related 순환은 서로 다른 규칙을 갖는다.
- SKOS의 preferred/alternate label, close match 개념은 용어 정리에 참고한다. SKOS의 직접 broader와 transitive broader는 구별되며, 애플리케이션의 순환 금지 정책도 별도로 명시한다. [SKOS Reference](https://www.w3.org/TR/skos-reference/)
- 기존 `same_as`를 `owl:sameAs`로 자동 변환하지 않는다. OWL의 동일성은 속성 추론에 영향을 주며, 현재 위키의 탐색용 연결과 다르다. 없는 근거는 거짓으로 단정하지 않는다. [OWL 2 Primer](https://www.w3.org/TR/owl2-primer/)
- 제안 파일 `src/graph-validation.ts`에 SHACL에서 참고한 종류·개수·경로 제약을 작은 로컬 프로파일로 둔다. RDF 변환과 실제 검증 엔진의 적합성 검사를 하지 않는 첫 단계는 **SHACL 호환 구현이라고 부르지 않는다**. [SHACL](https://www.w3.org/TR/shacl/)
- 기존 lint/예외 조회에 결과를 연결한다. 다섯 도구를 늘리지 않고, 새 endpoint가 꼭 필요한지도 먼저 검토한다. 자동 수정·병합·게시·과거 요약 입력 갱신은 하지 않는다.
- P2의 입력 리비전 일치와 현재 MOC 조사 범위를 각각 표시한다. 둘 중 하나가 참이라는 이유로 다른 하나를 참으로 표시하지 않는다.

검증: `src/graph-validation.test.ts`에서 숨겨진 대상과 없는 대상의 공개 오류를 구별할 수 없도록 검사한다. 필터 적용 후에만 집계한다. 부분 조사에는 조사 범위·중단 이유·제한된 후속 동작을 포함하며, 전역 무결성 검사를 완료했다고 표시하지 않는다. Markdown 예제 fence 내부는 기존 파서 규칙에 따라 제외한다.

## 4단계 — 코드와 함께 검증하는 UML

UML은 전체 클래스를 자동으로 나열하는 그림이 아니라 다음 네 가지 경계를 설명한다. 기준은 UML 2.5.1이며 문서 생성이 구현 검증을 대체하지 않는다. [OMG UML](https://www.omg.org/spec/UML/2.5.1)

| 문서 | 표현할 내용 | 드리프트 검증 |
| --- | --- | --- |
| 도메인 class | Note, Revision, Claim, EvidenceLocator, RelationOccurrence, MOCMembership, SynthesisBasis | 계약 필드·관계 이름·다중성 검사 |
| 검색 sequence | 인증 → 접근 가능한 후보 → 관계 발견 → 본문 읽기 → 리비전/ACL 재검증 → 반환 또는 폐기 | P1/P2 응답·경합 테스트 ID 연결 |
| 상태 state machine | 지식 lifecycle, task 상태, epistemic 상태를 각각 표현; preview/dry-run/fingerprint/apply 경계 | 실제 허용·거절 전이와 guard fixture 비교 |
| component/deployment | 다섯 MCP 도구 → endpoint registry → 서비스 → filesystem/접근 정책 → NAS; 로컬 파생 인덱스·Graphify 캐시 | 실제 import 경계와 배포 스크립트 계약 확인 |

제안 산출물은 `docs/architecture/uml/*.puml`, 설명 `docs/architecture/graph-contract.md`, 검사기 `scripts/check-architecture-contracts.mjs`, 테스트 `scripts/architecture-contracts.test.ts`다. 계약 버전과 관련 소스 해시를 기록하고, 요구사항→소스→검증 테스트를 연결한다. 테스트와 연결되었다는 표시와 최근 실행에서 통과했다는 증거를 분리한다. 단순 해시 검사만으로 sequence/state의 의미 일치를 보장하지 않으므로 전이 fixture 및 독립 검토를 함께 요구한다.

문서는 코드 기반의 개발 문서만 대상으로 하며 실제 Vault 내용·자격증명·호스트 비밀 설정은 넣지 않는다. class composition 표기는 NAS 원본의 연쇄 삭제 정책처럼 오해될 경우 사용하지 않는다.

최초 단계는 텍스트 원본과 계약 검사를 제공한다. 렌더러 설치는 별도 확인 후 고정 버전의 호스트 로컬 도구로만 수행한다. PlantUML 사용 시 SANDBOX 등 제한 프로파일로 파일/URL 접근을 막고, 외부 렌더링 서버로 코드를 전송하지 않는다. untrusted 문서의 include·실행 지시를 처리하지 않는다. [PlantUML Security](https://plantuml.com/security)

## 5단계 — 그래프 DB 필요성의 측정과 결정

실험은 기존 P1/P2/P3 완료 후 동일 자료·질의·호출자 접근 범위·응답 예산으로 수행한다. 새 저장소를 설치하는 실험 자체도 승인 후 진행한다.

1. 현재 인덱스의 cold build, warm query, 파일 하나 수정, 삭제, 별칭 변경, 권한 회수, 캐시 초과 경로를 분리 측정한다.
2. 로컬 합성 fixture의 문서 수·관계 발생 수·허브 분포를 고정한다. 1천/1만/5만 문서 규모는 제안이며 RAM 보호가 허용하는 단계까지만 실행한다. 실제 NAS 자료를 임의 복제하지 않는다.
3. p50/p95 지연, 프로세스 peak RSS, 구축/갱신 시간, 논리 읽기량, SMB 전송량을 별도로 기록한다. SMB 카운터는 호스트 공유 집계이고 캐시로 0일 수 있으므로 요청별 논리 I/O로 간주하지 않는다.
4. 기존 구현과 후보 저장소의 관계 종류·방향·복수 발생·모호성·정렬·부분 응답·현재 리비전을 비교한다. 보안/정답 동등성 실패는 성능 개선으로 상쇄하지 않는다.
5. 채택 기준의 초기 제안은 반복 측정 p95 20% 이상 개선, peak RSS 비증가, 검색 품질·보안 무회귀, 장애 시 원본만으로 재구축 가능이다. 이는 **제안된 기준이지 측정된 결과가 아니다**. 운영 비용까지 확인한 후 사용자와 최종 판단한다.

영속 파생 캐시를 검토한다면 원본/추출기/계약 버전과 인벤토리 변경을 추적하고, 호출자별 응답 캐시는 principal·정책 버전으로 분리한다. 캐시 적중 시에도 현재 접근권한을 검사한다. 로컬 투영의 원자적 교체와 NAS 전체의 원자적 트랜잭션은 구별한다. DB 장애가 원본 수정이나 접근권한 우회로 이어져서는 안 된다.

## 실행·완료 기준

- 권장 승인 단위: 1단계 계약 추출 → 2·3단계 표현/검증 → 4단계 UML → 5단계 측정 결과에 따른 별도 저장소 결정.
- 각 단계에서 인접 구현·테스트를 읽고 RED→GREEN, 대상 테스트, strict build, 전체 테스트, 독립 검토, `git diff --check`, staged 내용·비밀 검사, `npm run check:staged`를 순차 수행한다.
- 런타임 변경은 NAS 기반 배포, 원본/world/economy 보존 확인, rollback 보존, 실제 endpoint 검증 후 소스와 일치하는 `dist`를 함께 커밋하고 사용자 포크로 푸시한다. 문서만 변경하는 단계는 런타임 변경이 없음을 표시하며 배포했다고 과장하지 않는다.
- 공유 호스트 RAM 보호를 낮추거나 사용자 앱을 임의 종료하지 않는다. 코드·테스트·dist가 바뀌면 이전 검증 basis를 혼합하지 않는다. 임시 캐시·호스트 설정·자격증명·다른 작업의 문서는 커밋에서 제외한다.
- 독립 검토는 기존 검토 계정/절차를 사용한다. 새 작업자를 자동 증설하지 않는다. `llm_wiki`와 소유권을 확인한 후에만 공유 파일을 수정한다.

## 작성 시점의 기존 배포 상태 — 새 계획과 구분

현재 P1은 구현 및 대상 테스트·빌드를 마쳤지만 전체 검증이 **49/453 파일**까지만 완료됐다. 남은 검사가 RAM 안전 중단으로 지연되어 NAS 활성화·커밋·푸시는 아직 수행하지 않았다. P2/P3도 미착수다. 새 제안 문서 작성은 이 완료 조건을 대체하지 않는다. 자원이 확보되면 동결된 P1 basis의 미완료 검사부터 재개하고 기존 승인 순서대로 배포한다.

## 승인 후 실행 체크리스트

- [x] 선행 P1: 동일 basis의 잔여 전체 검사와 최종 평가, NAS 배포·실제 조회·커밋·포크 푸시.
- [x] 선행 P2/P3: 승인된 주제 패킷 및 로컬 Graphify 검증·배포 완료. P3는 호스트 전용 설치로 NAS 런타임을 바꾸지 않았음.
- [x] `llm_wiki`와 후속 Arkon 작업 및 본 계약 추출의 공유 파일 순서 재확인. 1단계 전달 후 Arkon 첫 묶음과 2단계 이상의 순서를 다시 조율.
- [x] 1단계: 기존 계약 characterization 테스트 → 공유 계약 추출 → 소비자 동등성 검증·배포. 소스/dist와 포크 전달은 본 변경의 Git 기록 참조.
- [ ] 2·3단계: 관계 발생 단위 및 검증 프로파일의 보안·리비전·복수 관계 테스트와 구현·배포.
- [ ] 4단계: UML 원본·드리프트 검사·전이 fixture·독립 검토.
- [ ] 5단계: 기존 인덱스 비용 측정 및 저장소 도입 여부 보고. 새 DB 설치는 하지 않음.

사용자가 현재 RAM이 최대 확보 상태라고 확인했다. 이전 4.8GiB 재시도 권장은 필수 조건에서 제거한다. 기존 시작/중단 보호값(3.8/3.5GiB)은 유지하면서 로컬 검증기의 npm 중간 프로세스를 제거하고 작은 비서버 테스트부터 순차 실행한다. 이 방식으로 14개 파일이 추가 통과해 63/453 파일까지 검증했다. 서버 통합 검사의 RAM 문제는 아직 해결되지 않았으며 전체 통과나 배포로 간주하지 않는다. 소스·테스트·dist 동결을 유지하고 검증 범위를 축소하지 않는다.
