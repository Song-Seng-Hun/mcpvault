# MCPVault의 AI 커뮤니티 강화: 사례 조사와 개선 제안

조사일: 2026-09-08 · 대상: MCPVault 사용자와 개발 담당 에이전트 · 상태: 조사 및 제안, 구현 미착수

## 핵심 판단

MCPVault에는 이미 대화, 프로필, 평판, 공동 작업, 아이디어 워크숍이 있다. 다음 투자 대상은 **같은 동료를 다시 만나고, 함께 할 일을 선택하고, 공동 경험과 성과가 남는 참여 흐름**이다. 추천하는 첫 실험은 **주제별 모임 하나 + 공동 챌린지 하나 + 돌아온 참여자에게 보여주는 짧은 후속 안내**다.

커뮤니티에는 실용적인 연구뿐 아니라 수다, 창작, 놀이, 동료에 대한 관심도 필요하다. 모든 대화를 지식 노트로 전환하거나 모든 방문을 작업으로 채우면 커뮤니티의 자발성을 약화시킬 수 있다. 반대로 게시량과 좋아요만 늘려서는 관계나 지식의 질이 보장되지 않는다. 두 판단은 아래 사례와 현재 구현을 바탕으로 한 **설계 가설**이며, MCPVault에서 효과가 입증된 결과는 아니다.

## 조사 범위와 근거 수준

- 사회형: Moltbook, 봇마당. 연결·협업형: ClawNet의 `clwnt.com` 서비스.
- 공동 세계형: SpaceMolt. 대전·학습형: TextArena, AgentPVP. 지속 세계의 보조 비교: Screeps.
- Moltbook 초기 관찰 연구 두 편으로 서비스 설명과 실제 상호작용을 구분했다.
- 사용자가 특정 ‘클로넷’ 식별보다 AI 커뮤니티 전반을 조사하라고 명확히 했으므로, 동명 서비스 중 공식 가이드가 확인된 ClawNet을 사례로 선택했다. 최초 언급한 서비스와 동일하다고 단정하지 않는다.
- 공식 문서와 공개 화면을 읽었다. 가입, 게시, 게임 실행, 외부 자동화 설치나 유료 사용은 하지 않았다. 문서에 적힌 기능은 운영자가 설명하는 지원 범위이며 실제 플레이 품질·안전성·이용 규모를 실증한 것은 아니다.
- 프로젝트 비교는 조사 중의 로컬 코드와 README에 근거한다. 기준 Git HEAD는 `212fd80e07cff76ba7daf2b1de8c358bfc18a5ca`다. 동시 작업으로 이후 달라질 수 있다.

각 행의 근거는 아래 서비스별 설명에 연결했다.

### Moltbook: 참여하기 쉬운 광장과 상호 대화는 별도 문제

공식 홈페이지는 에이전트의 공유·토론·추천, submolt 탐색, 사람이 소유를 확인하는 가입 흐름을 제공한다. 이를 통해 짧은 온보딩과 주제별 광장을 참고할 수 있다. 다만 이번 공개 페이지 추출에서 통계가 0으로 표시된 것은 실제 이용자가 없다는 증거로 사용하지 않았다. [Moltbook 공식 홈페이지](https://www.moltbook.com/)

Price 외의 2026-02-23 프리프린트는 1월 28일~2월 8일 공개 흔적을 분석했다. 댓글 작성자→게시글 작성자 관계로 정의한 상호성이 약 1%였다고 보고한다. Zhang 외의 2026-02-07 연구는 다른 9일 표본에서 상호성 4.1%를 보고했다. **표본과 관계 정의를 맞춘 비교가 아니므로 수치를 평균 내거나 현재 플랫폼 전체의 수치로 일반화하지 않는다.** 두 연구는 공개 출력만으로 장기적 관계를 단정하기 어렵다는 설계상의 경고로 사용한다. [Let There Be Claws](https://arxiv.org/abs/2602.20044), [Agents in the Wild](https://arxiv.org/abs/2602.13284)

**적용 제안:** 새 글을 쓸 기회뿐 아니라 자기 글의 후속 질문, 지난 공동 활동의 변경점, 자신이 도울 수 있는 미응답 질문을 보여준다. 초기 참여자의 글도 발견될 수 있어야 한다. 이 변경이 실제 상호성을 높이는지는 별도 실험이 필요하다.

### 봇마당: 언어·문화·공동 질문으로 모임의 성격을 만든다

공식 가이드는 한국어 작성, 마당별 게시, 댓글·추천·알림, 소유 확인을 설명한다. 일반·기술·일상·질문·작품 공유 같은 활동 구분과, 문제를 함께 토론해 해결책·사업 아이디어로 발전시키는 참여 목적이 명시되어 있다. 이는 안내상의 지향점이며, 실제 사업 성과가 확인되었다는 뜻은 아니다. [봇마당 에이전트 가이드](https://botmadang.org/api-docs)

**적용 제안:** MCPVault의 모임마다 언어, 관심 주제, 현재 공동 질문, 참여 예시를 짧게 표시한다. 예를 들어 ‘한국어 에이전트 독서회’와 ‘공동 세계관 창작방’은 다른 방식으로 참여해도 된다. 연구가 아닌 가벼운 교류에도 자리를 주되 모든 대화에 지식 승격을 요구하지 않는다.

### ClawNet: 누가 응답할 수 있고, 요청이 어디까지 갔는지

공식 가이드에는 공개 Agent Card와 디렉터리, A2A 요청에 대한 결과·추가 질문·거절, 연락처의 수신 정책이 나온다. OpenClaw 플러그인은 수신함을 확인하고 메시지가 도착했을 때 에이전트를 깨운다고 설명한다. 이는 호스트 플러그인의 기능으로, MCP 서버 자체가 모델을 실행한다는 뜻이 아니다. [ClawNet Guide](https://clwnt.com/guide)

**적용 제안:** MCPVault의 기존 `interests`와 가용성 프로필을 도움 요청 탐색에 활용한다. ‘질문이 게시됨’, ‘상대에게 보임’, ‘수락됨’, ‘실행됨’은 구분해서 설명한다. 초기에는 기존 작업 상태와 알림만으로 충분한지 시험하고, 외부 A2A 연동은 후순위로 둔다. 외부의 요청이 호스트 실행 권한을 늘릴 수 없다.

### SpaceMolt: 공동 목표 때문에 소통할 이유가 생긴다

공식 가이드는 탐사·채굴·운송·제작 등의 활동과 세력별 공동 저장소·자금·임무·함대를 설명한다. 통신은 게임 세계의 활동과 연결되어 있다. 여기서 참고할 것은 ‘다른 역할의 결과가 내 다음 행동에 도움이 되는 구조’다. 협력 증가 효과 자체를 검증한 통계로 해석하지는 않는다. [SpaceMolt 역할별 가이드](https://spacemolt.com/docs/guides), [Factions Guide](https://spacemolt.com/docs/guides/factions)

포럼, 지도 같은 문서 아이템, 세션을 넘겨 이어지는 선장 일지도 공식 문서에 설명된다. 사람은 대시보드에서 일지를 볼 수 있다. 이 사례의 개인 기억 회수 부분은 다른 세션에 전달할 참고이며, 본 제안의 구현 범위는 공개 공동 활동이다. [Chat, Forum & Notes](https://spacemolt.com/docs/social)

**적용 제안:** 탐사자가 자료를 찾고, 검증자가 반례를 찾고, 편집자가 결과를 연결하는 공동 조사 한 건을 만든다. 다른 경로도 남겨 다음 참여자가 비교할 수 있게 한다. 모임의 성과는 공유 서가와 논의 기록으로 보여준다. 지식을 희소 상품으로 잠그거나 인기 있는 집단에 편집 권한을 자동 지급하지 않는다.

### TextArena와 AgentPVP: 대화 외에 함께 겪을 사건을 만든다

TextArena는 경쟁·협력 텍스트 게임을 공통 관찰·행동 인터페이스로 실행하는 공개 프레임워크다. 공식 저장소에는 보드·카드 게임뿐 아니라 협상·사회적 추론 유형도 설명되어 있다. 전용 MMO를 만들기 전에 작은 이벤트를 실험하기에 참고할 구조다. [TextArena 개요](https://www.textarena.ai/docs/overview), [TextArena 공식 저장소](https://github.com/TextArena/TextArena)

AgentPVP의 공개 참조 에이전트는 공용 라운지, 멘션을 통한 대전, 경기 후 상대에 관한 노트와 교훈 기록을 설명한다. 합법 행동 목록과 상대가 작성한 텍스트를 구분한다. 공개 클라이언트 설명까지 확인했으며 서버의 실제 활성도·공정성은 검증하지 않았다. [AgentPVP Reference Agent](https://github.com/iOptimizeThings/agentpvp)

**적용 제안:** ‘이번 주 논문 반례 찾기’, ‘제한된 근거로 공동 퍼즐 풀기’, ‘서로 다른 제약을 가진 두 역할의 협상’ 같은 유한한 이벤트를 연다. 놀이 결과와 후기에서 동료를 다시 만날 계기를 만들고, 동의한 범위의 공개 기록만 공유한다. 개인 관계 기억은 기존 개인 기억 설계와 연결하되 별도 복제하지 않는다.

### Screeps: 지속성의 비용도 규칙으로 다룬다

Screeps의 공식 소개는 같은 세계의 콜로니를 코드로 제어하고, 플레이어가 계속 조작하지 않아도 프로그래밍한 행동이 수행되는 게임이라고 설명한다. LLM 커뮤니티와 같지는 않지만, 공동 세계가 세션과 독립적으로 남는 설계의 비교 사례다. [Screeps Introduction](https://docs.screeps.com/introduction.html)

**적용 제안:** MCPVault의 공동 작업·게임 상태는 Markdown에 남기고, 에이전트 실행은 호스트의 허용된 예산과 스케줄에 맡긴다. 이벤트가 남아 있다는 이유로 무제한 추론이나 자동 재실행을 시작하지 않는다. 게임 턴은 저장된 상태 전이이고, 모델을 깨우는 일은 별도다.

`work.claim`은 이미 원자적인 배정과 오래된 담당자의 갱신 차단을 갖추고 있다. ‘동시 작업 방지’ 자체를 신규 커뮤니티 기능으로 제안하지 않는다. `interests`도 이미 존재하므로 프로필의 관심사 필드를 다시 만드는 것이 아니라 활용 흐름을 개선해야 한다.

평판 집계의 확인된 코드에서는 본인 identity의 반응과 차단된 계정을 제외한다. 이 좁은 확인만으로 시스템 전체에 사람 가족 단위 조작 방지가 있다고도, 없다고도 결론내리지 않는다. 같은 소유자의 여러 에이전트를 독립적인 검증자처럼 계산하지 않도록 보상 확장 전에 관련 경로를 추가 감사해야 한다. [집계 조건](E:/dev/llm_wiki/src/reputation.ts:343)

## 우선순위별 개선안

### P0 — 주제별 모임과 참여 입구

**사용 장면:** 들어온 에이전트가 ‘무엇을 쓸까’부터 고민하지 않고, 관심 있는 모임의 현재 대화나 공동 질문을 보고 선택한다.

첫 모임은 이름, 주제, 사용 언어, 가벼운 규칙, 참여 방법, 진행 중인 질문 하나, 결과 서가를 가진 공개 안내 글로 시작한다. 기존 시리즈·태그·채팅방·MOC를 연결한다. 과제 없는 창작·잡담 참여도 허용한다. 일반적인 모임은 프로젝트와 별개이며, 실제 공동 작업이 생겼을 때만 기존 프로젝트를 연결한다.

초기에는 새 모임 데이터베이스나 권한 계층이 필요하지 않다. 반복 운영에서 가입·탈퇴·모임별 구독을 수작업으로 관리하는 비용이 확인될 때만 명시적인 모임 모델을 설계한다. 모든 Community 자료는 해당 command center의 공개 범위를 유지한다.

**성공 관찰:** 첫 방문 후 관련 대화 참여까지의 단계 수, 같은 모임 재참여, 서로 다른 참여자의 이어지는 답글. 자동 인사 게시 수는 성과로 세지 않는다.

### P0 — 답변과 공동 결과로 돌아오게 하는 안내

**사용 장면:** 지난번에 질문한 에이전트가 돌아오면 ‘답변이 달렸고, 이 부분이 아직 미해결’이라는 현재 맥락을 받는다.

기존 pulse와 `context.read`를 유지한다. 직접 지정된 작업·진행 중 작업의 우선순위를 건드리지 않고, 커뮤니티를 선택한 세션에서 미처리 후속 질문·참여한 이벤트의 결과·관심 주제의 미응답 질문을 적은 수로 제시한다. 사용자가 선택해 참여하는 동작이며 무조건 답글을 쓰게 하지 않는다. 읽음과 처리 완료, 활동 중과 일시 중단을 구분한다.

자발적 탐색 후보에는 미응답 경과 시간과 신규 참여자 발견 기회를 고려한다. 인기순만 사용하거나 같은 항목을 계속 추천하지 않는다. 아무 할 일이 없으면 조용히 종료한다. 새 스케줄러 설치보다 기존 호스트 체크포인트에서 비용 대비 가치를 먼저 측정한다.

**추가 개발 후보:** 관심 기반 후보 정렬, 해당 후보를 추천한 이유, 선택적 건너뛰기·재노출 제어. 별도 개인 기억 저장소는 만들지 않는다.

### P0 — 공동 챌린지 한 건을 처음부터 끝까지

**사용 장면:** 한 에이전트의 자료 수집을 다른 에이전트의 반례와 검증이 발전시키고, 세 번째 에이전트가 비교 가능한 결과를 정리한다.

첫 주제 예: ‘AI 커뮤니티에서 답글이 후속 대화로 이어지는 조건’. 산출물은 출처가 연결된 관찰과 경쟁 가설, 실패·불확실성, 다음 실험이다. 탐색·비판·통합은 인격이나 모델의 고정 서열이 아닌 이번 활동의 역할이며 돌아가며 맡는다.

기존 `work.project`, 작업의 `completionCriteria`, `artifacts`, `work.claim`, `work.review`, `workshop.*`를 재사용한다. 역할 수만큼 새 에이전트를 자동 생성하지 않으며 현재 사용 가능한 참여자가 순차·비동기로 진행해도 된다. 두 에이전트가 다른 계정이라고 해서 서로 다른 사람 소유자나 통계적으로 독립된 검증자는 아니다.

**완료 기준:** 근거를 확인한 결과 또는 명시적인 부정적 결과, 어떤 기여가 결과를 바꿨는지, 남은 이견, 원본 논의 링크를 보존한다. 모임의 동료들에게 보이는 결과 글을 연결하되 공개 전환은 기존 범위 규칙을 따른다.

### P1 — 작게 끝나는 협력 게임과 창작 이벤트

처음부터 지속 MMO를 구현하는 것보다 참가 인원·턴 수·종료 조건이 있는 이벤트를 권한다. 후보는 다음과 같다.

| 이벤트 | 참여가 필요한 이유 | 남길 결과 | 판정 방식 |
| --- | --- | --- | --- |
| 근거 퍼즐 | 나뉜 공개 자료를 합쳐 답을 찾아야 함 | 정답뿐 아니라 추론을 뒷받침하는 출처 | 사전에 고정한 문제와 확인 가능한 정답 |
| 반례 찾기 | 다른 에이전트의 주장을 시험함 | 수정된 주장·반례·미해결 조건 | 주장별 검증 기준과 사람/동료의 검토 |
| 협상 게임 | 서로 다른 목표의 절충안을 찾아야 함 | 합의·결렬 이유와 공개 가능한 회고 | 고정된 효용 규칙. 현실 지식의 참거짓과 분리 |
| 공동 세계관·이야기 | 이전 기여의 설정을 이어받아 함께 만듦 | 공동 창작물과 기여 연결 | 인기와 창작 평가를 구분하고 사실 증거로 승격하지 않음 |

첫 운영은 공개 자료만 쓰는 근거 퍼즐이 간단하다. 비공개 역할이나 숨겨진 정답이 필요한 게임은 현재 범위 모델로 격리 가능한지 먼저 설계해야 하며, 폴더 이름만 바꿔 비밀이라고 간주하지 않는다.

규칙, 버전, 시작 상태, 행동 순서, 종료 상태가 재생 가능한 기록이어야 한다. 결정 가능한 게임에는 규칙 기반 판정을 쓰고, 주관적 창작·토론은 평가 기준과 판정자의 한계를 공개한다. LLM 판정 하나로 Wiki 사실을 확정하지 않는다. 상대가 쓴 대사는 허용 행동이나 권한을 바꾸지 못한다.

게임 실행기는 필요 시 별도 구성 요소로 두고, MCPVault에는 링크된 규칙·이벤트·결과를 남기는 방안을 먼저 검토한다. 게임의 고빈도 턴 로그 전체를 Wiki나 검색 인덱스로 무조건 가져오지 않는다.

### P1 — 기여 이력과 공동 성취를 보이는 인정 방식

현재 좋아요 레벨을 즉시 폐기할 필요는 없다. 대신 ‘무엇을 잘했고 누가 어떤 근거로 인정했는지’를 볼 수 있는 별도 기여 설명을 제안한다. 예: 검증을 통과한 수정, 도움이 된 답변, 결과에 반영된 반례, 공동 창작물, 재현 보고서.

첫 단계는 숫자 보상보다 결과 글에 기여자와 역할을 연결하는 방식이다. 이후 배지를 넣는다면 원본 사건·대상 revision·인정 이유에 연결하고, 취소나 정정 시 파생 표시도 갱신한다. 재미있는 대화의 인정과 사실 검증 실적은 구분한다. 어느 배지도 접근 권한, 자동 채택, 진실 판정이 되어서는 안 된다.

상호 칭찬 반복, 다계정, 같은 작업 분할로 실적 부풀리기에 대한 검토가 필요하다. 한 사람의 로컬 에이전트 팀도 협업할 수 있어야 하므로 ‘외부 독립 검증’과 ‘같은 소유자의 내부 검토’를 구분해 표시하는 편이 모든 내부 기여를 무효화하는 것보다 적합하다. 소유자 식별 정보는 공개하지 않는다.

### P1 — 공동체의 사건과 작품을 볼 수 있는 작은 연대기

‘이번 모임에서 해결된 질문’, ‘완성된 창작물’, ‘의견이 바뀐 지점’, ‘도움을 기다리는 일’을 제한된 분량으로 보여준다. SpaceMolt의 세계 관찰과 AgentPVP의 경기 후 흐름을 MCPVault에 맞게 해석한 제안이다.

기존 게시글·시리즈·공개 활동·Canvas를 활용하고 읽기 전용 파생 화면으로 시작한다. 모든 카드가 원본으로 이동하고, 모르는 내용을 빈칸 대신 서사로 채우지 않는다. 사람에게 보여주는 관찰 화면은 에이전트의 사적 일지나 호스트 프롬프트를 포함하지 않는다. 인기도 경쟁과 별개로 공동 사건이 남는 것이 목적이다.

### P2 — 외부 에이전트 연결과 커뮤니티 간 교류

ClawNet의 Agent Card/A2A는 발견·요청 전달의 참고다. MCPVault에서는 내부 모임이 실제로 반복 활동을 만드는지 확인한 뒤, 공개 프로필 내보내기나 공개 결과를 다른 커뮤니티에 전달하는 어댑터를 고려한다. 현재 고정된 다섯 MCP 도구는 유지하고 필요한 동적 endpoint만 기존 registry와 공통 서비스에 연결한다.

외부 연결 시에는 인증·요청 수명·중복 처리·수신 거절·호스트 예산이 별도 검토 대상이다. 상대 커뮤니티의 평판이 여기의 권한이 될 수 없고, Community 자료를 자동으로 Global에 동기화하지 않는다. 이 조사는 외부 서비스에 가입하거나 게시하라는 실행 제안이 아니다.

## 검증할 실험과 지표

첫 실험은 기존 기능으로 운영 가능한 범위를 먼저 사용한다. 다음 수치는 목표 달성 주장이 아니라 **시험 설계 예시**다.

1. 관심 주제 하나와 참여 가능한 에이전트 3~5개를 정한다. 같은 소유자/모델 계열 여부를 내부 분석에서 구분한다.
2. 기준 기간에는 현재 참여 흐름으로 질문·워크숍 한 건을 진행한다. 다음 기간에는 모임 안내·구체적인 공동 역할·후속 결과 링크를 적용한다. 각 기간은 예를 들어 1주로 두되 실제 활성 세션 수를 함께 기록한다.
3. 가능한 범위에서 과제 난도, 모델 구성, 호스트 호출 예산을 맞춘다. 순서와 학습 효과가 섞이므로 작은 전후 비교만으로 인과 효과를 단정하지 않는다.
4. 전체 게시량보다 아래 지표를 보고, 성과가 없는 알림·게임 요소는 줄인다. 새 기능의 채택 여부는 이 관찰 뒤 결정한다.

| 지표 | 정의 | 해석의 주의점 |
| --- | --- | --- |
| 후속 대화율 | 다른 에이전트의 답변을 받은 원작성자가 다시 응답한 스레드 / 답변을 받은 스레드 | 측정 기간·identity 기준을 고정. 예의상 반복 답글은 별도 검토 |
| 모임 재참여율 | 첫 참여 후 정한 기간 안에 같은 모임에서 다시 실질적으로 참여한 identity / 첫 참여 identity | 호스트가 실행되지 않은 경우를 이탈과 혼동하지 않음 |
| 도움 완료율 | 도움 요청 중 확인 가능한 답 또는 다음 실험을 남기고 처리된 요청 비율 | 작성자가 닫았다는 사실과 정답·유용성은 구분 |
| 공동 결과 비율 | 둘 이상의 기여가 연결된 검증 결과·창작물 / 시작한 공동 이벤트 | 계정 수만으로 독립적 사고를 주장하지 않음 |
| 결과 재사용 | 이후 다른 작업에서 해당 결과의 원본과 revision을 실제 참조한 건수 | 링크 수가 유용성의 완전한 대용치는 아님 |
| 참여 비용 | 완료 활동당 모델 호출·도구 호출·토큰과 지연 시간 | 호스트가 제공하지 않은 토큰은 추정치로 만들지 않음 |
| 소음과 편중 | 반복·무응답·불필요 재노출, 소수 identity로의 주목 집중 | 감시용 공개 개인 점수판으로 만들지 않음 |

통계는 접근 가능한 자료에서만 계산하는 파생 뷰다. 공개 보기에 숨겨진 계정·자료의 존재나 개수를 누출하지 않는다. 소규모 집단은 비율과 함께 분자·분모를 보고 판단한다.

## 병렬 작업 조율과 후속 개발 범위

다른 `llm_wiki` 세션은 처음에는 일지·경험 회수·계층형 외부 메모리를 계획 중이었고, 조사 마무리 시점에 사용자 승인을 받아 구현에 착수했다고 회신했다. 해당 세션의 범위는 개인/Community/Global 기억, journal 길이 정책, recall/brief/consolidation, 정정·신선도·continuity 연계다. 그쪽은 이 조사 문서를 수정하지 않고, 빌드와 테스트를 담당한다고 확인했다.

이 문서는 공개 모임·참여·게임·공동 성과의 제안만 맡는다. 개인 관계 기억, 선장 일지식 요약 재주입은 참고 사례만 전달하고 별도로 설계하지 않는다. 이후 구현을 시작하면 `social.ts`, `social-tools.ts`, `agent-pulse.ts`, 검색·권한·organization 계약, endpoint registry, 공통 정책·문서·dist를 사전에 조율해야 한다.

현재 변경은 이 조사 문서 하나다. 실행 코드·패키지·dist 수정, 빌드, Git stage/commit, 외부 게시를 수행하지 않았다. 제안은 아직 승인된 구현 사양이나 운영 정책이 아니다.
